## Mission
Produce (1) a complete, evidence-backed decode of the game Star Command (QuickBASIC 3.00 modules + BRUN30.EXE runtime, 1988, Winston Douglas Wood) as BASIC-style pseudocode plus data-format specs, and then (2) a playable, faithful reproduction. Form of the product (decided): custom engine, **HTML5 canvas + vanilla JavaScript**, EGA-faithful 640x200 16-color upscaled, keyboard + Gamepad API, zero install, runs in Chrome on the handheld PC. Acceptance (ruling SC-1 = B, the owner 2026-10-15) = same content, layout and behaviour per screen as the original run in DOSBox; palette/resolution enhanced to 640x200 EGA 16-colour. Evidence: the original runs in SCREEN 1 (CGA 320x200, 4 colours) in every module except PLBATTLE (SCREEN 7, 320x200 16-colour); the .EGA sprite banks are the art source, the .BAS/CGA banks are reference only (see decode/data/SPRITES.md).

Gate rule: **no game-building until the decode gate is met** (every module's pseudocode complete, every runtime routine the game uses named with evidence or explicitly marked unknown, every data file format specified, screens inventoried). Rulings for the owner go into `RULINGS.md` (one question, options A/B, your recommendation first); the coordinator relays them.

## Methodology (REA: Reverse Engineer Anything)
- Every claim is **Evidence** with provenance (file, offset, bytes, routine body) or an explicit **unknown**. No invented names. Confidence H/M/L on every naming; see `decode/brun30/RT_LEDGER.md` for the format and the conventions already proven.
- Tools: REA CLI + Ghidra 12.1.4 live in WSL Ubuntu (`wsl.exe -d Ubuntu -- bash <script>`; env in `~/bin/rea-mcp`; GHIDRA_INSTALL_DIR=~/tools/ghidra_12.1.4_PUBLIC). Capstone (python3-capstone) in WSL. Windows Python 3.13 for file parsing. Scripts: `decode/tools/*.py` (mz.py, qbdis.py, rt_asm.py, ctx.py, dis16.py), `decode/ghidra_scripts/BrunExport.java`.
- Targets: `<targets>\starcommand\starcoma\` (WSL `/mnt/c/...`). Never modify originals. 7 modules: STARCOMM (launcher, 288 B code), STARTUP (3.8 KB), SPACE (39 KB), STARPORT (44 KB), INSIDE (29 KB), PLBATTLE (43 KB), SPBATTLE (30 KB). Data: 78 .BAS + 16 .EGA = BSAVE'd GET-array sprite banks (header FD seg off len; body = GET arrays: w(bits),h, 4 EGA planes), 4 .STR, 1 .BAT.
- Known so far (proven, see ledger): module header 0x40 bytes, code at 0x40, size = header word1 paragraphs; INT 3D/3E/3F + inline byte = runtime call through tables at BRUN 0x171/0x243/0x38D; RT3F_71/85/95/9D take one extra inline byte; LOCATE/PRINT/float assign/compare/mul/cint/csng named; graphics PUT family partially; string assign. 140 routines used by the game, ~25 named.

## Work plan (phase 1 = decode; phase 2 = build)
1. **Runtime naming (lane rt-naming):** finish `decode/brun30/RT_LEDGER.md` for all 140 used routines using `decode/brun30/rt_asm.txt`, `decode/brun30/funcs/*.c`, `decode/brun30/used_routines.tsv`, and game-side contexts (`decode/tools/ctx.py`). Output: ledger rows + `decode/brun30/rt_names.json` (feeds qbdis listings).
2. **Data formats (lane data):** sprite banks (.BAS/.EGA GET arrays) → `decode/data/SPRITES.md` + PNG renders (`decode/data/png/`), .STR files, .BAT, and the string/constant areas of each module (string-literal init table: `len,descriptorAddr,text`). Map which module BLOADs which file (search listings for the filename string descriptors).
3. **Module pseudocode (lanes mod-startup, mod-space, mod-starport, mod-inside, mod-plbattle, mod-spbattle):** one lane per module, sequential if lanes are scarce, smallest first (STARTUP proves the format). Input: `decode/listings/<MOD>.lst` (regenerate with `python3 decode/tools/qbdis.py` after the names map changes). Output: `decode/pseudo/<MOD>.bas.md` = BASIC-style pseudocode with line labels = code offsets, variables named by evidence (string literals, usage), every runtime call rendered as the BASIC statement it implements, screens/flows inventoried in `decode/pseudo/<MOD>_SCREENS.md`.
4. **Verification (lane verify):** independent re-read of 10% random lines per module against the listing; discrepancies → fix or mark unknown. Then write `DECODE_GATE.md` with the checklist; the coordinator declares the gate to the owner.
5. **Build (phase 2, after gate; the owner 2026-10-15: do NOT wait for a go-ahead once `DECODE_GATE.md` is complete):** first write `BUILD_PLAN.md` (engine architecture, screen list in module order, sprite pipeline from the .EGA banks (the owner/coordinator 2026-10-15: the engine loads sprites from a PNG atlas + JSON index with a scale factor, data-driven, no sprite data in code, so an upscaled or redrawn art set can be swapped in later without code changes; the art pass itself is deferred), input map incl. Gamepad API, acceptance per screen under SC-1 = B), then start phase-2 lanes immediately (Opus unless a task needs Fable). the coordinator reports the plan to the owner when BUILD_PLAN.md lands. `RULINGS.md` is for genuine decisions only. `game/` HTML5 engine: EGA palette + 640x200 text/graphics modes, BASIC-screen emulation (LOCATE/PRINT/COLOR), sprite PUT/GET, keyboard/gamepad; then screens in module order; side-by-side screenshots vs DOSBox for acceptance (`ACCEPTANCE.md`, per screen).
